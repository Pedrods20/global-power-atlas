# Project review — 2026-09-13

The platform is substantial and reproducible, but the next increment should
repair data semantics and delivery guarantees before adding models or markets.
Passing the existing tests is evidence for the cases they cover; this review
found reproducible failures outside those cases. Findings below are not fixes.

## Findings that change the next sprint

### 1. High — European resolution inference corrupts mixed-resolution windows

[`energy_charts.py`](../src/gpa/sources/energy_charts.py#L139) assigns one inferred
resolution to every price row in a request. Power parsing uses the same window-wide
approach. A request spanning a resolution transition can therefore label hourly
observations as quarter-hourly. The schema accepts both values and cannot detect
the semantic mistake.

Measured in the committed local price history:

| Zone | Rows labelled 15 minutes with a following timestamp 60 minutes later | UTC span |
|---|---:|---|
| DE-LU | 557 | 2025-09-07 17:00 to 2025-09-30 21:00 |
| FR | 550 | 2025-09-08 00:00 to 2025-09-30 21:00 |
| ES | 550 | 2025-09-08 00:00 to 2025-09-30 21:00 |

A synthetic response at minute offsets `[0, 60, 120, 135, 150, 165]` returns
`resolution_min=15` for all six rows. The official
[DE-LU response for 2025-09-15](https://api.energy-charts.info/price?bzn=DE-LU&start=2025-09-15&end=2025-09-15)
returned 24 prices spaced by 60 minutes during this review. This corroborates
the parser diagnosis; it does not replace verification of every affected window.

The forecasting panel rejects incomplete hourly coverage, so it excludes these
rows rather than repairing them. Other duration-weighted metrics consume the
incorrect duration directly. Fix source resolution handling with explicit
transition/gap cases, re-fetch affected windows from the provider, and regenerate
all dependent outputs. Do not infer that every long gap is a longer interval.

### 2. High — Several metrics still violate the duration/DST conventions

[`load.py`](../src/gpa/metrics/load.py#L140) uses a row mean for load factor and
row rank for duration curves; price duration curves reuse that helper. The
[`volatility`](../src/gpa/metrics/price.py#L322) calculation also uses a row mean
for daily prices and differences consecutive observed dates without requiring
consecutive calendar days.

[`capture_rate`](../src/gpa/metrics/price.py#L400) combines prices and generation
by local date and clock hour, merging the two distinct autumn delivery hours
before calculating revenue. It also averages subhourly prices before weighting
generation, so exact interval revenue and this hourly approximation differ.

Reproduced counterexamples:

| Input | Current output | Duration/interval-aware result |
|---|---|---|
| 100 MW for 60 minutes, 0 MW for 15 minutes | Load factor 0.50 | 0.80 |
| Same observations in a duration curve | 100 MW at 50% of observations | 100 MW for 80% of observed time |
| The two DE-LU autumn 02:00 deliveries: prices 0/100, wind 1/9 MW, each 60 minutes | Capture price 50; capture rate 1.0 | Capture price 90; capture rate 1.8 |

The exact aggregate impact on every published market has not been measured.
Add independently calculated regression cases, preserve distinct UTC delivery
instants while grouping reporting periods in market time, and label any hourly
capture approximation explicitly. Recompute README figures after correction.

### 3. High — The workflow does not preserve successful data on every failure

The Python pipeline continues after a target fails and writes successful targets.
But the CLI exits nonzero if any target failed, and
[`ingest.yml`](../.github/workflows/ingest.yml#L47) then skips validation,
export and commit under the normal success-only step condition. A benchmarks
or export failure likewise prevents persistence. The existing commit-before-
freshness ordering protects only a later freshness failure.

If freshness fails after a successful commit, the
[`Deploy` condition](../.github/workflows/deploy.yml#L26) refuses the failed ingest
run. The new valid observations remain in Git while the hosted site stays behind.
Also, push deployment runs independently of CI and checks out moving `main`,
so a successful deploy is not evidence that the same revision passed CI.

Define the desired failure behavior explicitly: validate and persist successful
targets, report failures without hiding them, and deploy a specific validated
revision according to that policy. Exercise partial failure, freshness breach,
export failure and a concurrent push. Keep GitHub Actions; these are workflow
ordering problems, not reasons to introduce Airflow.

### 4. Medium — The current forecast API cannot issue forecasts without targets

[`Panel.complete()`](../src/gpa/forecast/panel.py#L129) requires the target price
as well as every feature. Both ridge and LightGBM use this frame to select
prediction rows. `build_panel` also starts from observed target prices.

With the existing synthetic test panel, forecasting 2025-02-10 produces two rows
for each fitted model. Making that day's target unknown, with all features
unchanged, produces zero rows. This is a limitation of the retrospective API,
not evidence of training on future target values.

Prospective operation needs a delivery grid independent of target availability,
a separate feature-only prediction path, persisted `issued_at`/delivery instants,
input versions, model configuration and later scoring. Missing inputs should
produce explicit abstentions. The existing tests for temporal separation remain
valuable, but do not test this issuance path.

### 5. Medium — A fixed end date does not freeze the benchmark data

`BENCHMARK_END` limits delivery dates, while every export rebuilds the panel
from the latest upserted observations. Replacing only September DE-LU partitions
with the already-published remote ingest, keeping the end date unchanged,
changed the panel SHA-256:

- Local: `d891960f87329ab566389cf79acb2ad86f3ad238f15c9e4e41af8e632e6b2e6f`
- Remote data at the same cutoff: `3ca9ca94dfd777d7a8869f3dbc2103c34519dd9bfa30131b165691ff80c751e8`

Late observations and revisions can change a capped historical experiment.
Keep an immutable input/configuration snapshot for each experiment; use a
different identifier for a refreshed retrospective result. Optional MLflow
already records useful snapshots, but ordinary site export does not use one.
Separate routine dashboard export from expensive benchmark reruns or cache by
an explicit data/configuration hash. Lock the experiment environment as well:
Python dependencies currently specify ranges, not a reproducible resolved set.

### 6. Medium — Source drift and completeness need checks beyond schema/freshness

Energy-Charts silently drops unknown generation labels rather than mapping or
flagging them, despite the documented `other` fallback. It accepts both `Load`
and `Load (incl. self-consumption)` and sums them if both appear. A synthetic
payload of 100 and 110 MW produces 210 MW; a new generation category disappears.
These are conditional parser defects, not proof that current load is doubled.

Freshness checks the latest timestamp per zone/dataset. It cannot detect a
missing fuel, an internal gap or incorrectly labelled durations when another
recent observation exists. Carbon's known-factor coverage checks reported energy,
not unreported or silently discarded generation. Add temporal coverage, source
category drift and a deterministic load-definition policy. Storage writes also
go directly to the destination Parquet; atomic replacement is a useful smaller
reliability improvement.

## What remains worth keeping

The static architecture fits the current volume. Source separation, canonical
contracts, UTC storage with local market calendars, explicit manual CCEE handling,
carbon-factor coverage, negative-price preservation and common-sample forecast
comparisons are useful foundations. The quality gates and local MLflow artifact
tests provide a practical base for correcting the gaps above.

The local retrospective scores remain ridge MAE 21.06, LightGBM 22.18 and best
naive 28.43 EUR/MWh on 7,982 shared cells. Ridge is the leading point model on
this sample. LightGBM loses to the best naive baseline in negative and scarce
regimes. Their empirical 80% intervals cover about 75–76% of calibrated cells.
These are development findings on the current inputs, not prospective acceptance
or economic value, and input repairs require a new experiment version.

## Proposed sequence for discussion

1. **Correct data and metrics.** Resolve the European interval transition,
   duration curves/load factor/volatility and capture alignment. Acceptance:
   provider-backed repaired windows, independent numerical cases, coverage
   report, regenerated exports and updated analytical claims.
2. **Finish reliable delivery.** Integrate the remote ingest, regenerate rather
   than choose conflicting derived Parquet files, repair partial-failure handling,
   and couple deployment to a validated revision. Add browser smoke to automation;
   it is currently a local command, not a CI step. Then publish and verify hosted
   desktop/mobile behavior.
3. **Create prospective evidence.** Retain a versioned retrospective snapshot,
   implement target-independent issuance and begin collecting forecasts/inputs
   before auction prices are known. Agree the evaluation period and acceptance
   criteria before inspecting its results. Operator demand/wind/solar forecasts
   are the next input investigation, subject to actual availability and timestamps.
4. **Choose analytical depth deliberately.** Residual-load charts and ramps
   reuse existing data; the residual-load helper already exists for forecasting.
   Battery perfect-foresight value can be a separate upper-bound study after
   interval correctness, with efficiency, power, energy and state-of-charge
   constraints. Forecast-based trading value requires prospective evidence.

Keep ERCOT/PJM prices pending credentials, Tokyo physical series pending a source
assessment, and Californian thermal spreads pending an appropriate fuel basis.
They add breadth but do not resolve the current credibility issues.

Reframe Front B before implementing it: its proposed ANEEL/ONS/CCEE documents
are Brazilian, while the only price-forecast benchmark is DE-LU. There is no
specified feature path from that corpus to the target. A Brazilian prediction
study needs a Brazilian target and explanatory variables; a regulatory research
assistant instead needs retrieval/provenance evaluation. This review proposes
discussing that distinction, and does not reverse the recorded forecasting-before-
retrieval decision or authorize a new product direction.
